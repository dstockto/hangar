It works before you configure anything.

Hangar gathers hosts from four places and merges them. Every one is on by default, because a source that finds nothing costs nothing.

Hosts you already have

Nothing to set up.

  1. Hangar reads ~/.ssh/config on first launch every Host block, and the files it Includes
  2. They become searchable and grouped behind the same shortcut as everything else
  3. Your file is never rewritten those hosts already resolve; Hangar leaves them alone
  4. Git remotes are recognised and skipped github.com is not a machine you ssh into

Hosts on a spreadsheet

One drag.

  1. Drop a CSV anywhere on the window
  2. alias or hostname is enough user, port, product, env and role if you have them
  3. Any other column becomes a tag group the menu by datacenter, or owner
  4. A row that cannot be written safely is refused by line number, never silently dropped

An AWS fleet

Where it gets interesting.

  1. One read-only ec2:DescribeInstances
  2. Aliases built from your tags so they survive the instance being replaced
  3. Denied? Systems Manager is tried on its own and finds on-prem hosts EC2 never could
  4. A dashboard over the same response no second call, no second permission

Your key never touches disk.

If an ssh agent is holding your key, Hangar finds it and uses it. 1Password, Secretive and anything on SSH_AUTH_SOCK go through the same path. There is no CLI to install and nothing to configure.

What Hangar writes

Three lines, per host.

# ~/.ssh/config.d/hangar Host payments-prod-sftp HostName sftp.prod.example.com IdentityAgent "…/1password/t/agent.sock" IdentityFile ~/.hangar/keys/deploy.pub IdentitiesOnly yes

IdentityFile names the public key. With IdentitiesOnly that is how ssh is told which of the agent's keys to offer, so a vault holding a dozen of them does not run past MaxAuthTries and fail on a host that would have worked.

What happens when you connect

The vault signs; nothing is read.

$ ssh payments-prod-sftp ssh asks the agent to sign 1Password asks you to approve ✓ authorized with Touch ID [deploy@sftp ~]$

Hangar never reads, exports or stores a private key. It asks the agent what it holds the way ssh does, over the agent socket. The only thing it writes is the public half, under ~/.hangar/keys.

Thousands of hosts to the right one.

A hand-kept ssh config goes stale and an autoscaling group replaces the hostname you saved. Either way the lookup is the work, and you do it again every time. Search stays under half a millisecond per keystroke at ten thousand hosts.

Without Hangar

Every single time.

  1. Remember roughly what the box is called was it web, webapp, or www?
  2. aws ec2 describe-instances --filters … then read JSON to find the one you want
  3. Copy a 58-character hostname ip-10-0-42-17.us-west-2.compute.internal
  4. ssh ec2-user@… and hope the login is right
  5. The instance is replaced tomorrow and the hostname you saved is gone

With Hangar

Four seconds, from any app.

  1. Press ⌘⇧H
  2. Type payments prod web terms match in any order
  3. Press ↩ the first match is already selected
  4. You are on the box in iTerm2 or Terminal, with the right login
  5. Tomorrow the alias still works it follows the tags, not the hostname

Built for the way you already work.

Standard SSH underneath. Nothing to learn, nothing to migrate.

Fuzzy fleet search

Terms match in any order across alias, hostname and tags. Type the three things you remember.

query pay prod web match payments-prod-web-1 from 2,847 hosts in 2.8 ms

Stable SSH aliases

Hangar owns one ssh_config include and rewrites it on every sync, so terminated instances drop out on their own.

# ~/.ssh/config.d/hangar Host payments-prod-web-1 HostName web-1.prod.example.com User deploy

Native terminal launch

Return opens a real session in iTerm2 or Terminal. ⌘↩ copies the command instead.

$ ssh payments-prod-web-1 Last login: Tue 09:14 from 10.0.0.9 [deploy@web-1 ~]$

Four ways to find a host

EC2, Systems Manager, the hosts already in your ssh config, and any CSV you drop on the window. No AWS permission at all is required, and a denied call falls back on its own instead of showing you an error.

EC2 denied Systems Manager 31 hosts ~/.ssh/config 41 hosts hosts.csv 18 hosts

1Password, with no setup

If an ssh agent is holding your key, Hangar finds it and uses it. One key is adopted without asking. No op CLI, and no private key is ever read, exported or stored.

# ~/.ssh/config.d/hangar Host payments-prod-web-1 IdentityAgent "…/1password/t/agent.sock" IdentityFile ~/.hangar/keys/prod-sre.pub IdentitiesOnly yes

Credentials stay local

The same resolution order the AWS CLI uses, read straight from your home directory, with the signing done here. Expired SSO tokens refresh in place, so the CLI is only needed for the first aws sso login on a machine.

env skip ~/.aws/credentials skip sso profile work resolved

⌘-click a host to set its user or key. Detect Login probes the usual cloud images and keeps the one that authenticates.

The whole fleet, out of the call you already made.

Hangar lists your instances once and keeps the answer. The dashboard is everything that one response can tell you, so it costs no second API call and no second permission: ec2:DescribeInstances, read only, is all Hangar ever asks for.

The aliases work everywhere ssh does.

Hangar writes standard ssh_config. Anything that speaks SSH picks the aliases up, whether Hangar is running or not.

$ scp deploy.tar.gz payments-prod-web-1:/tmp/

Nothing is uploaded.

Hangar reads what is already on your machine and writes one file. There is no other side to it.

  • No Hangar server It talks to AWS and to GitHub for updates. Nowhere else.
  • No account, no telemetry Nothing to sign up for and nothing reported back.
  • Private keys are never read Key material stays with ssh and your agent. With 1Password, only the public half of the chosen key is written, and it is asked for over the agent socket rather than read from the vault.
  • Read-only against AWS One ec2:DescribeInstances call, signed with SigV4. That is the only IAM permission Hangar asks for, and it works without one.
  • One generated file ~/.ssh/config.d/hangar, written at 0600 after ssh itself validates the syntax.
  • Your own config is left alone Hosts imported from it are launched, never rewritten, so Hangar can never outrank a file you wrote by hand.
  • Tags are untrusted input Values are quoted on the way into ssh_config and shell-quoted on the way into a terminal. An imported host and a CSV row are held to exactly the same rules.
  • Signed and notarized Updates install only when Apple notarized them and the signing team matches.

Three steps, no toolchain.

No Homebrew, no Xcode, no xattr workaround. The app is signed with a Developer ID certificate and notarized by Apple.

And one step to undo it. Settings → Uninstall Hangar removes ~/.hangar, the aliases it generated, and the Include line it added to your ~/.ssh/config, then moves the app to the Trash. Your AWS credentials and the rest of that file are untouched.
